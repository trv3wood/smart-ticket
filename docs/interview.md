# 面试讲解

## 3 分钟项目介绍

“我做了一个面向客服团队的工单管理后台，管理工单创建、处理状态流转和审计记录。后端使用 Java 21、Spring Boot、MyBatis，数据可用 MySQL 持久化，详情采用 Redis cache-aside；本地提供 H2 模式，方便稳定演示。

核心业务是创建、接单、解决、关闭和重开，每次变化都有审计记录。我把状态规则放在枚举中，更新时使用 version 乐观锁。状态更新和审计写入处于同一事务，测试验证了八个并发请求只有一个成功，以及审计失败时状态会回滚。

列表用了基于 id 的游标分页和 status、id 联合索引，避免大 OFFSET，也不每次查询总数。缓存写入设置随机 TTL，提交之后删除缓存；Redis 不可用时可以回源，但并发回填仍可能读到旧值，所以写路径不会使用缓存校验。

后续可以加入团队权限隔离、创建幂等键及通知模块。”

## 常见追问

**为什么不是微服务？** 当前业务规模小，一个可验证的模块化单体更容易保证事务与演示稳定性。先证明需要独立扩容或团队边界，再拆分通知服务。

**为什么不用 synchronized？** 它只能约束单个 JVM。版本号条件在数据库里原子判断，多个应用实例也可以竞争同一行。

**乐观锁一定更快吗？** 低冲突时避免显式持有应用锁；高冲突时会频繁失败。应根据冲突率决定锁策略，不能泛称更快。

**缓存删除为何要放在提交之后？** 提交前删除可能让另一请求读到未更新的数据并回填。afterCommit 避免这种特定窗口，但不能消除所有并发旧读回填。

**Redis 宕机时怎么办？** 捕获缓存操作异常，读请求回源数据库；仍需限流或熔断保护数据库。本项目设置短超时，但未实现完整热点保护。

**为什么状态在前、id 在后？** 查询先按状态等值筛选，再按 id 范围和倒序输出。可减少排序或扫描；要用实际执行计划验证，不能单凭索引存在就声称覆盖索引，列表还查询 title 等字段。

**为什么不 COUNT？** 演示只需知道是否还有下一页，limit=size+1 足够；总数属于另一种产品需求。

## 简历写法

仅在你确实阅读、运行并能解释后使用：

> 工单管理后台（个人项目）｜Java 21、Spring Boot、MyBatis、MySQL、Redis。实现工单状态流转和事务审计，采用版本号控制并发更新；设计联合索引与游标分页；实现 Redis 详情缓存及故障回源。编写并发冲突与事务回滚测试。

不要写“生产 QPS 万级”“准确率 95%”“大规模微服务”“实习上线”或其他未实际测量/经历的内容。压测结果要一起注明机器、数据量、并发、鉴权方式和错误率。

## 面试前 30 分钟

1. 运行 demo.py，逐项解释响应和 409。
2. 找到 Mapper 的版本条件和 Service 的事务边界，说明审计失败行为。
3. 跑 MySQL 优化实验，读懂实际扫描行数与时间。
4. 查看 Redis key 与 TTL，更新后验证缓存删除。
5. 熟悉边界：单团队权限、创建非幂等、缓存非强一致。
